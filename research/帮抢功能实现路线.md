# 帮抢功能：无刷新、单次点击的复用方案

更新日期：2026-10-13。状态：已检查现有发布包并检索开源项目；尚未连接学校登录页面或执行报名。

## 最新需求

- 在尚未结束、仍可参与或即将开放报名的活动旁显示“帮抢”。报名结束时间与活动结束时间分别判断；不向已经截止报名的活动提供任务入口。
- 点击“帮抢”后记录活动、账号及报名开始时间，显示“已预约”和取消入口。
- 报名开始后，在现有页面执行一次浏览器鼠标点击，不自动刷新，不重复提交。
- 次数范围暂按“同一账号对同一活动只尝试一次”设计，仍待用户确认是否实际要求“一个账号总共只能安排一次”。
- 用户此次关于不刷新的要求覆盖旧设计文档中的刷新流程。

## 从现有 EXE 中确认的事实

使用本机已有 PyInstaller 的 CArchiveReader 静态读取应用模块，没有运行提取出的应用代码。原模块名为 edge_activity_dashboard.py；提取出的 21,418 字符侧栏脚本保存为 extracted/overlay.v4.3.js。这是嵌入的脚本文本，不是完整恢复的 Python 工程。

学校入口常量为 https://study.gdipu.edu.cn/CloudPortal/CloudSquare 。网页检索工具无法访问此入口，真实页面行为仍未检查。

脚本中的问题和需求差异：

1. 第 263–270 行明确先保存 refreshing，再调用 location.reload()；这是现有实现的固定行为。
2. 第 202–209 行在多个文档中查找文字为“报名”或“立即报名”的第一个按钮，没有将按钮限定到活动 ID；只检查 disabled，不足以判断页面全部禁用状态或遮挡情况。
3. 第 216 行采用 DOM button.click()；没有使用浏览器输入引擎的鼠标操作。
4. 第 315 行任务只有 state、title、at、autoConfirm，没有 accountId、activityId 或已执行任务的唯一约束。保存单个 localStorage 对象不能实现可靠的按账号、活动防重复。
5. 第 217 行可能额外自动点击确认；实际报名是否需要确认框必须在真实页面检查，区分“一次鼠标点击”和“一次完整报名尝试”。

本地依赖也显示：pywebview 的 edgechromium.py 第 87–90 行支持 REMOTE_DEBUGGING_PORT；本机 Python 3.12 已安装 Playwright 1.61.0，尚未安装 APScheduler。发布包使用 Python 3.14，独立辅助进程可避免直接混用这两个 Python 环境。

## 开源组件比较

| 项目 | 已核对的能力 | 与本项目的关系 |
| --- | --- | --- |
| microsoft/playwright-python | 浏览器元素定位、鼠标操作；官方明确支持通过 CDP 连接 WebView2 | 首选。优先连接现有程序，复用它的页面和登录会话；实际 EXE 的连接能力仍需验证 |
| agronholm/apscheduler | 一次性 DateTrigger 定时任务 | 使用稳定版本的既有调度器；配合本地记录限制执行次数。主分支 v4 当前标注预发布，不直接作为生产依赖 |
| g1879/DrissionPage | Chromium 页面自动化，模拟点击和 JS 点击两种模式 | 备选。需核对选定版本的默认模式和回退行为；当前文档对部分默认值描述不一致，不直接照抄默认调用 |
| asweigart/pyautogui | 控制系统鼠标和键盘，支持单击 | 如果确实要求操作可见系统鼠标，可选这条路线；需要前台窗口、坐标和显示缩放稳定，容易受用户操作干扰 |

此次检索没有核实到一个能直接适配“广轻 3.0”的完整开源成品。检索到的通用连点器、其他网站抢票脚本不能直接提供该站的活动识别和账号限制。采用以上成熟组件作为依赖，保留上游实现，不重写浏览器控制或调度引擎。

## 推荐架构

现有 EXE / WebView2 → Playwright 连接当前页面 → 活动卡片上的“帮抢”入口 → APScheduler 一次任务 → 账号与活动记录 → 一次鼠标点击 → 页面结果识别。

可以先做独立辅助进程，验证连接现有 EXE；不必等完整 Python 源码恢复。官方文档支持启动 WebView2 时通过进程环境变量启用 CDP。调试连接仅供本机使用，按目标进程、页面 URL 和活动标识选择页面，不能简单地对 contexts[0].pages[0] 发送点击。

仅接管已有 WebView2 时，优先复用其运行时，不额外下载浏览器。不要启动旧版的“安排一次报名”任务，以免其旧刷新逻辑与新任务同时执行。取得原始工程后，将辅助逻辑整合到正式启动和打包流程。

## 实施顺序及完成条件

1. **连接与页面核对。**连接现有 WebView2，确认登录会话、活动列表、活动 ID、报名时间字段及目标按钮。只读检查时不触发真实报名。检查跨域 iframe、页面是否自动更新报名状态、是否存在二次确认。
2. **先确认无刷新可行。**提前打开选定详情并保留页面，观察开始时间到达后按钮是否自然可用。如果页面必须重新加载才更新状态，就如实报告此限制；不通过强制移除 disabled 假装页面已经开放。时间判定使用明确的 Asia/Shanghai 时区，检查系统时钟偏差；调度器不保证精确到某一毫秒。
3. **接入一次点击。**复用 Playwright 元素定位和状态检查；到时重新确定按钮可见、启用、未被遮挡且属于选定活动，获取当前坐标，再调用一次 page.mouse.click(..., click_count=1)。该方法组合鼠标移动、按下和松开，属于浏览器输入，不保证控制屏幕上可见的系统光标，也不保证与真人操作在所有方面相同。
4. **建立防重复记录。**以账号标识和活动 ID 建唯一记录；点击前通过本地事务将任务标记为已领取执行。点击发送后即使网络超时或结果不明，也不自动再发一次。允许漏执行但不盲目重发，严格区分“已尝试”“学校确认成功”“结果待确认”。本地记录只能约束共享该记录的程序实例，无法保证其他设备或其他程序不再报名。
5. **添加活动入口。**只在符合报名条件的活动旁显示“帮抢”，用稳定活动 ID 关联任务；重新渲染页面时避免重复插入按钮。点击后显示活动名称和时间；任务触发前可取消；账号变更、活动页被关闭或身份无法核对时停止。卡片没有报名开始时间时，需要先读取相应详情才能完成预约。
6. **验证并交付。**先在本地页面验证不刷新、仅一次点击、重复预约、延迟启用、遮挡、进程重启和账号切换。真实学校页面的报名动作只针对用户明确选择的活动。最后完成正式打包和源码提交；推送 GitHub 所需登录独立处理，不作为检索公开项目的前置条件。
